# 故障验证

通过 `./mvnw -Pmysql-it verify` 运行数据库测试，设置 CAMPUS_FULL_IT=true 后启用完整服务用例。服务容器应使用独立测试库、Redis DB 15 和测试虚拟主机，避免与业务数据混用。下表区分已编写的验证和人工实验方法，结果以具体运行日志为准。

| 场景 | 操作与要检查的结果 |
| --- | --- |
| 并发争抢 | BookingApiIT 同时发送 24 个预约争 3 个名额，核对 3 条有效订单、占用为 3 |
| 同一订单并发取消 | 两次均读到取消状态，数据库只释放一次；之后可重新预约 |
| Redis Lua 竞争 | FullBookingIT 验证同用户重复、入口满额，以及错误令牌无法释放别人的额度 |
| Redis 查询回填与失效 | 连续查两次，确认 Redis 命中；预约提交后再查，确认剩余名额变化 |
| MQ 无路由 | 暂时移除测试绑定；发布虽可能确认，但 return 令请求保留在发件表；恢复后重新发送并成功 |
| 提交后重复投递 | 在确认订单已经提交后再次发布同一编号，检查消费确认计数增加，订单仍只有一条 |
| 消费阶段写入失败 | 定向注入数据库访问异常；经真实 broker 重试两次后进死信，持久化请求 FAILED，没有订单 |
| 候补过期 | 令测试 offer 到期，禁止确认；回收后下一位得到 offer，名额没有重复释放 |

人工演练可在独立演示环境中停止 Redis 或 RabbitMQ，再恢复。Redis 不可用时直接预约仍由 MySQL 保证，full 就绪检查会报告依赖异常。RabbitMQ 不可用时，数据库可用则先保存已受理请求，恢复后尝试继续发布；超过截止时间会失败并释放入口租约。数据库不可用时不能接受新请求。重启 Redis 不改变已提交订单。单节点示例不证明 broker 高可用或跨数据中心容灾。
